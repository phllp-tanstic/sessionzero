# Prospective trajectory capture contract v1 — specification only

Status: **READY_TO_IMPLEMENT as a contract; NOT IMPLEMENTED OR DEPLOYED**. This freezes the capture evidence needed by the accepted [trajectory redesign](RESEARCH_REDESIGN.md), without changing `decision_snapshot.v1`, the deployed worker, the accepted 21-member cohort, or the `FIRST_1M_BAR_OPEN` outcome. No State, Confidence, Fair Value, Gap, Conviction or trading model is part of this contract. A future implementation must pass migration, local integration, operational timing and restore gates before deployment. All historical diagnostics remain RETROSPECTIVE ESTIMATED.

## Identity, slots and schedule

Contract IDs: `prospective_trajectory_capture.v1`, `prospective_trajectory_bar.v1`, `prospective_trajectory_snapshot.v1`, `trajectory_slot_schedule.v1`. XNYS via the pinned trading-calendar provider determines the *previous regular close* C and *next scheduled regular open* O for each `cash_session_date`. Slot instants are computed as UTC instants from those calendar boundaries, never hardcoded UTC hours. The preceding session may be separated from O by a weekend, holiday or early close. Every planned slot must satisfy C < T < O; invalid or duplicate slots fail schedule construction. The slot list is frozen independently of results:

| slot_id | Scheduled T | Reason |
|---|---|---|
| `CLOSE_PLUS_2H` | C + 120 min | Early repricing after cash close. |
| `CLOSE_PLUS_6H` | C + 360 min | Intermediate overnight checkpoint. |
| `OPEN_MINUS_6H` | O − 360 min | Overnight-to-premarket bridge. |
| `OPEN_MINUS_3H` | O − 180 min | Later path checkpoint. |
| `OPEN_MINUS_2H` | O − 120 min | Short pre-open evolution. |
| `OPEN_MINUS_1H` | O − 60 min | Exact legacy decision-time compatibility. |

`OPEN_MINUS_30M` is **not captured in v1**: the accepted 1H archive showed the same latest strictly completed bar as at −1h, so it adds no price observation under this cadence. It may be a new version only after a genuinely eligible higher-frequency source and measured latency justify it. No synthetic interim price is allowed.

One `trajectory_slot` row per cash session and slot binds `slot_id`, date, C, O, `scheduled_timestamp=T`, `calendar_version`, `universe_version`, `cohort_version`, `mapping_version`, source-evidence version, expected 21 symbols, schedule version and status. Every capture attempt records UTC `actual_capture_start`, `actual_capture_end`, `worker_run_id`, `git_commit` and per-source request counts. To qualify as a snapshot at T, capture starts in the declared `[T−15 minutes,T)` window and **finishes strictly before T**. Railway may start late; a late completion is never relabeled on time. These timestamps are stored, not inferred from provider event times. A separate per-symbol status records partial coverage; aggregate `CAPTURED` requires all 21 planned symbols under the declared eligibility policy.

The current Railway cron `*/5 12-14 * * 1-5` cannot visit close+2/+6, weekend-anchored slots or most overnight checkpoints. The minimum correct simple proposal is a five-minute UTC wake **every day**, with the worker deriving slots from the previous/next XNYS sessions. It creates up to 288 wakes/day (8,640 in 30 days), most no-ops; this is a planning load, not an authorization to change cron. Railway documents UTC cron, five-minute minimum spacing, possible lateness, and skipped starts while the prior execution remains active ([cron contract](https://docs.railway.com/cron-jobs)). A later narrower UTC envelope may be accepted only after proving coverage of DST, weekends, holidays and early closes.

## Immutable raw-path observation contract

For every provider request, retain exactly one immutable raw response envelope with endpoint, query parameters *without secrets*, provider symbol, category/interval/type, request start and response ingestion times, provider `requestTime` or request ID when available, response payload, collector version, Git commit, slot/run ID, and envelope hash. The raw envelope is not copied once per returned bar. A response's provider timestamp is not asserted to be each bar's publication time. Bound page size/retries, clip to the requested half-open interval and preserve boundary-spillover telemetry; no missing bar is fabricated.

For each validated returned Reality bar, append or reuse an immutable canonical version with:

`source=bitget`, `provider_symbol`, `market=SPOT`, `interval=1H`, `bar_type=market`, `event_start`, `event_end=event_start+1H`, decimal-string OHLC, nullable decimal-string volume/turnover, `logical_key_hash`, `canonical_hash`, `version_hash`, first request/ingestion time, first envelope ID, source-session assessment/evidence ID/version/publication time, collector version and Git commit. A link associates every envelope with every canonical bar it returned. Null volume/turnover is not zero. Identical content deduplicates the observation version but retains each new retrieval; changed content appends a new version. `UPDATE`/`DELETE` on evidence tables must be rejected by database trigger, with FK `RESTRICT`. Original upstream revision history before first ingestion remains unknown.

The exact previous cash-session `LAST_1M_BAR_CLOSE` is the native context requirement. Capture it once as early as possible after the previous close, then refer to its immutable *as-ingested* version at each subsequent slot. If its first capture is late, it can support only later slots. A later correction appends a version and cannot rewrite earlier snapshots. Record native feed `sip`, `1Min`, `adjustment=raw`, exact final-minute event time, request/ingestion times, raw Alpaca response and safe request ID. Optional trailing native context is **not** required by this v1 contract; adding it requires a separate feature/capture version and proof that each field was available before T. Corporate actions with unknown publication time remain excluded.

## Snapshot reconstruction and identity

The canonical eligibility boundary is **`event_end < T`**, matching the existing T−60 `decision_snapshot.v1` policy. A bar ending *at* T is excluded because its full OHLC, provider processing and delivery cannot be assumed known at that exact instant. A qualifying version must additionally have `request_start <= ingestion_time <= actual_capture_end < T`; only a retrieval already ingested by the frozen capture cutoff may be selected. When multiple versions of one logical bar exist, select the latest ingestion no later than that cutoff, with a deterministic retrieval-hash tie-breaker. Later corrections are visible in the audit history but cannot enter an earlier snapshot. Source-session evidence must be symbol-scoped, effective for the entire relevant path, published **and ingested** before the cutoff; later-learned metadata cannot upgrade an earlier path. `UNKNOWN` or conflicting evidence stays visible and cannot be silently converted to open. The exact anchor bar at C and native previous close must be present or the trajectory is explicitly incomplete.

`ProspectiveTrajectorySnapshotV1` is **one symbol × cash session × slot**. It contains `symbol`, native ticker/mapping identity, `cash_session_date`, `slot_id`, T, `actual_capture_start/end` and `feature_cutoff=actual_capture_end`; exact previous-close version hash; latest eligible Reality version hash; the chronologically ordered `(event_end, version_hash)` path from C through T; expected/observed/missing hourly boundaries; source-session assessment/evidence IDs and versions; calendar, universe, cohort, mapping, dataset, schedule, capture and schema versions; sorted capture-run IDs and raw-envelope hashes; and literal `contains_future_outcome=false`. No native next open, future bar, fitted state, strategy decision or PnL field exists. A snapshot may carry an explicit incomplete-quality status, but cannot claim a complete path without its exact anchor, native close, and qualified source evidence.

Snapshot identity is SHA-256 of canonical UTF-8 JSON (sorted keys, UTC ISO-8601 timestamps, decimal strings, explicit nulls) over the above immutable *semantic* fields, including the actual cutoff, sorted run/envelope IDs, and path pairs sorted by `(event_end,version_hash)`. Database insertion order does not enter the hash. A unique `(symbol,cash_session_date,slot_id,schedule_version)` selects the first frozen canonical snapshot; repeats append retrieval evidence or an attempt status but never replace it. If a later same-slot attempt has different content, retain the discrepancy as separate evidence, not as a rewrite or a second production-style as-known snapshot. Path observation links have FK constraints and are separately indexed by version/time. All snapshot/evidence rows are append-only.

An outcome is **not** a snapshot input. The canonical `FIRST_1M_BAR_OPEN` is the open of the exact first SIP/raw regular-minute bar at O, distinct from an official auction print. The existing outcome collector waits until O+17 minutes, retrieves and versions it, then append-links the outcome to eligible snapshot versions. The future trajectory implementation must allow that same once-per-symbol outcome retrieval when **either** a legacy v1 decision snapshot **or** at least one valid trajectory snapshot exists; the current collector's legacy-snapshot precondition cannot suppress outcomes for earlier captured slots if T−60 was missed. Earlier snapshots remain byte-for-byte unchanged. A missing or corrected outcome changes the outcome ledger/linkage only; no pre-open feature record is edited.

## Slot failure semantics

Status is recorded for every scheduled slot, plus per symbol; no success is inferred from an absent row. Use the following precedence when an attempt has several failures: `IDENTITY_MISMATCH` or `DATABASE_FAILURE` prevents valid persistence; otherwise `MISSED_SLOT` for no in-window complete attempt; otherwise source/adapter statuses determine per-symbol completeness. Preserve independent error codes and counts rather than hiding mixed causes.

| Status | Exact interpretation |
|---|---|
| `CAPTURED` | In-window, pre-T immutable evidence and snapshot meet the declared slot eligibility for all planned symbols. |
| `PARTIAL` | Some but not all 21 per-symbol snapshots are complete; retain valid evidence, never call the aggregate complete. |
| `PROVIDER_UNAVAILABLE` | Bounded provider call failed or returned no valid required data; no synthetic fallback. |
| `SOURCE_SESSION_UNKNOWN` | Effective/publication evidence is absent, conflicting or learned after cutoff; bars may be retained as observations but not certified source-open. |
| `SOURCE_SESSION_CLOSED` | Effective-dated evidence explicitly establishes source closure; retain status, do not invent a candle. |
| `MISSED_SLOT` | No valid capture finished strictly before T; later requests may support later slots only. |
| `DATABASE_FAILURE` | Required transaction could not commit; emit a redacted operational log and record the failure only when storage returns, without backfilling the slot. |
| `IDENTITY_MISMATCH` | Cohort, mapping, calendar or schedule identity differs from the frozen manifest; stop before provider use where possible. |

A provider failure after some symbols is `PARTIAL` with individual provider errors. A slot missed over a weekend stays missed even if the next slot fetches those old bars. A capture that completes after T is `MISSED_SLOT` for prospective status, though its raw retrieval may be retained under the later actual ingestion time if safely persisted separately. Retry cannot change a frozen snapshot.

## Request and storage budget (21 symbols)

The normal close-to-T−60 period has about 17 eligible hourly completion boundaries per symbol; a Friday-to-Monday interval can have about 65. Full-path read at each of six slots needs **126 Bitget requests per next cash session** (one per symbol per slot) when one page suffices, plus **21 Alpaca native-close** requests once and **21 later outcome** requests: **168 planned provider requests/session** before retries. A transitional separate legacy T−60 capture would add 21 Bitget **and 21 Alpaca** requests, raising the total to **210**; the implementation should share T−60 provider evidence while preserving the old snapshot. Longer holiday paths or provider spillover can require bounded additional pages, so 168 is not a hard maximum. Bitget documents 20 history requests/sec/IP and 100 rows/page; 21 paced calls within a 15-minute capture window are plausible but must be verified end-to-end ([market-data contract](https://www.bitget.com/docs/catalog/market/market-data)).

Normal-session unique canonical Reality bars are approximately `21×17=357`; a long weekend can approach `21×65=1,365`. Full-path requests repeat bars across slots, about `21×(2+6+12+15+16+17)=1,428` returned bar entries normally and roughly `21×(2+6+60+63+64+65)=5,460` after a weekend, subject to actual source availability. There are up to 126 per-symbol snapshots and 126 slot-status entries, plus one aggregate row per slot and 21 close/21 outcome versions/retrievals. A sample accepted archive has median **87 bytes of raw provider bar payload** and **303 bytes of normalized candle JSON**; these measure serialized source content, **not PostgreSQL row/index/WAL size**. Thus raw bar payload alone is about 0.12 MB normal or 0.48 MB long-weekend per session; normalized unique candle JSON is about 0.11/0.41 MB. Raw envelopes, path-hash links, revisions, indexes, WAL and backup copies dominate beyond those floors.

Planning allowance: **roughly 1–3 MB of primary DB growth per normal cash session, 3–8 MB after a long weekend, or ~30–100 MB per 20–22-session month**, plus WAL, backup retention, no-op worker rows and unexpected provider spillover. This is an order-of-magnitude estimate, not measured remote usage or a capacity guarantee. All-day five-minute cron means up to 8,640 worker starts/month and potentially that many small operational rows unless no-op writes are suppressed in a future version; CPU/startup costs may exceed data-storage costs. The current PostgreSQL engine and persistent volume are **SUFFICIENT as an architecture for this cohort**, but free capacity, indexes, backups and restore point must be measured before enabling capture. Railway bills volume, compute, memory and backup/egress separately ([billing](https://docs.railway.com/pricing/understanding-your-bill), [PostgreSQL/backups](https://docs.railway.com/databases/postgresql)). No claim is made that the current subscription has verified spare capacity or a working restore point.

## Deployed-worker delta and minimal evolution

| Required field/capability | Present? | Change required | Migration? | Scheduler? | Provider request? |
|---|---|---|---|---|---|
| XNYS calendar, 21-member identity, previous close, T−60 timestamp | Yes | Reuse; do not reinterpret old snapshots | No for old rows | Add other slots | No for legacy T−60 |
| Six-slot date-relative schedule, weekend/early-close resolution and per-slot statuses | No | Add slot planner and status ledger | Yes | Yes: broader daily wake | No for planning |
| Immutable every-bar Reality OHLCV with completion, raw envelope and correction versions | Only selected T−60 mark/raw response | Add one-envelope/many-bar path capture and time/version policy | Yes | Each slot | Yes: bounded full path |
| Native close as an early as-known context version | Only at T−60 | Capture at first qualifying slot and reuse hash; later corrections append | Yes for new links | First slot | Early Alpaca call |
| Source-session status/evidence as known at *each* slot | Only T−60 | Persist assessed evidence, publication and ingestion per slot/symbol | Yes | Each slot | No new provider required for curated evidence |
| Per-symbol trajectory snapshot, path links, missingness and deterministic hash | No | Add new versioned type/table, preserve legacy `decision_snapshot.v1` | Yes | Each slot | No separate request beyond path |
| Append-only outcome link to all eligible trajectory snapshots | Only old decision snapshot | Allow outcome collection if either snapshot type exists; add separate links after O+17m and keep old links | Yes | Existing outcome window | Existing outcome request can be reused |
| Independent second source | No | Separate acceptance/mapping/rights gate; not in trajectory v1 | Later version only | Later | Not now |

Smallest evolution: preserve `sessionzero-prospective-worker tick` and its v1 T−60/outcome path, but add a date-relative slot planner, a trajectory capture operation, new append-only tables, and an outcome-link fan-out after the existing once-per-symbol outcome retrieval. Reuse the cohort verifier, provider clients, source-session resolver, PostgreSQL transaction style, redacted logs and calendar. Maintain one canonical frozen snapshot per symbol/slot and durable attempt statuses. Do **not** loosen old v1 schema checks or rewrite `capture_iteration`; build a separate v1 trajectory contract alongside it. The current `session_on(today)` planner is insufficient for weekend/holiday-anchored slots and must be replaced for the new operation with previous/next-session resolution. This is a proposal, not code.

Proposed migration (no tables created now): `trajectory_slots` (unique session/date/slot/schedule version, scheduled time and aggregate status), `trajectory_capture_runs` (attempt times, status, identity, source counts, error codes), `trajectory_raw_envelopes` (one provider request/response and safe metadata), `trajectory_observation_versions` (Reality bars and native-close versions, with source/role/event start/end/content hashes), `trajectory_retrieval_observations` (many-to-many envelope↔observation versions), `trajectory_snapshots` (one immutable symbol/slot record with semantic hash and `contains_future_outcome=false`), `trajectory_snapshot_observations` (ordered path links with FK), and `trajectory_outcome_links` (append-only link to the existing outcome-version table). `RESTRICT` FKs, uniqueness, timestamp/role constraints and UPDATE/DELETE rejection are required. Existing `point_in_time_*`, `decision_time_snapshots`, `prospective_outcome_*` and old outcome links remain untouched. This uses more tables than simply extending a field enum because existing v1 tables enforce one selected mark/close per decision and one raw response per retrieval; loosening those constraints would weaken historical evidence.

## Backward and research compatibility

An existing `decision_snapshot.v1` at T−60 is a valid **`LEGACY_MARK_ONLY`** evidence view: it supplies one as-ingested Reality mark and previous-close hash at its actual capture time, plus later append-only outcome linkage. It is **not** a complete trajectory and must not be filled with historical bars retrieved later. New snapshots may coexist at T−60 in separate tables; their logical identity is distinct. During rollout, current v1 capture/outcome links continue and no migration rewrites old records. A new T−60 snapshot may reference the same raw retrieval where a future implementation proves exact shared evidence; it cannot claim raw path bars that the old snapshot did not retain as canonical versions.

With all required captures, a future research process can compute decision-time Reality displacement and path quality, reconstruct evidence quality and observed state-transition inputs, and join *later* first-minute opens to calculate direction/transfer/residual labels and mark-error targets. It can then test state-correctness and price-reliability calibration in separately frozen chronological research. These are **capabilities of the data contract**, not validated models. If a source slot is missed, path/status features remain explicitly incomplete. Dynamic source leadership and source agreement remain unsupported until an independent, licensed, aligned second feed passes [the gate](SOURCE_LEADERSHIP_GATE.md).
